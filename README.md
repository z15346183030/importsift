# importsift

**Put every import in its place — and show why it went there.**

One file. No dependencies. No configuration file. Python 3.10+.

```console
$ python importsift.py src/
sorted      src/shop/app.py
1 file(s) checked, 1 changed, 0 with no imports
```

---

## The problem this solves

Which group an import belongs to is not a matter of taste. `import os` is
standard library, `import requests` is third-party, `import shop.models` is
your own code — those are facts about your interpreter and your files.

Most import sorters treat the question as a preference, so they ask you to
answer it in a config file: `known_first_party`, `src_paths`,
`default_section`. Then the same file with the same config produces
different output on a laptop and on CI, because the answer is derived from
the *working directory* rather than from the file.

`importsift` never asks. It looks:

| Question | Where the answer comes from |
|---|---|
| Is it standard library? | `sys.stdlib_module_names`, generated by CPython itself |
| Is it my code? | Is there a file or directory for it, walking up from the file being sorted |
| Is it installed? | Is it in a `site-packages` on the path |
| Is it relative? | Does the statement start with a dot |

Nothing else is consulted. Not the working directory, not a config file, not
a list of names someone maintained by hand.

## Install

There is nothing to install. Copy `importsift.py` next to your code, or:

```console
$ curl -O https://raw.githubusercontent.com/z15346183030/importsift/main/importsift.py
```

Python 3.10 or newer is required — that is when `sys.stdlib_module_names`
arrived, and using it is the point.

## Use

A bare run rewrites files in place:

```console
$ python importsift.py .
sorted      src/shop/app.py
sorted      src/shop/models.py
14 file(s) checked, 2 changed, 0 with no imports
```

Anything that prints a report never writes. `--check`, `--diff`, `--explain`
and `--json` are all read-only.

```console
$ python importsift.py --check .        # exit 1 if anything would change
$ python importsift.py --diff app.py    # unified diff, file untouched
$ python importsift.py --explain app.py # where each import goes, and why
$ python importsift.py --json app.py    # same information, for tooling
$ python importsift.py --merge .        # also join from-imports of one module
```

### `--explain`

This is the part the other tools keep to themselves.

```console
$ python importsift.py --explain src/shop/app.py
src/shop/app.py
  line    1  thirdparty  requests            unresolved: not on any path
  line    2  thirdparty  dj_rest_auth.views  unresolved: not on any path
  line    6  stdlib      os                  os in sys.stdlib_module_names
  line    7  local       .                   relative import, level 1
```

`requests` is not installed here, and it is still third-party. That is
deliberate: whether a package happens to be installed does not change who
owns it, and keeping the two apart is what makes the answer stable between
your machine and the build server.

### The five sections

| Order | Section | What lands there |
|---|---|---|
| 1 | `future` | `from __future__ import ...` |
| 2 | `stdlib` | anything in `sys.stdlib_module_names` or `sys.builtin_module_names` |
| 3 | `third-party` | installed in a `site-packages`, or not found anywhere |
| 4 | `first-party` | a module or package inside your project |
| 5 | `local` | `from . import x`, `from ..pkg import y` |

Within a section, `import x` lines come before `from x import y` lines, each
sorted by module name, case-insensitively. One blank line separates
sections. That is the whole ordering rule.

## What it will not do

The interesting part of an import sorter is the list of things it refuses.

**It never re-serialises an import.** A statement, its trailing comment and
the comment lines directly above it are moved as one block of untouched
text. This is why this:

```python
from dj_rest_auth.views import (
    LoginView,
    LogoutView,
    # PasswordChangeView,
    # PasswordResetConfirmView,
)
```

comes out of a sort looking exactly the same, only in a different place.
A tool that parses the statement and prints it again has to decide what to
do with those two commented-out names, and the usual answer is to fold them
into a single inline comment.

**It never reorders the names inside a statement.** Sorting
`from x import (b, a)` means rewriting that line, and rewriting that line is
where comments get eaten.

**It verifies before it writes.** The rewritten file is parsed again and the
set of `(level, module, name, alias)` tuples is compared with the original.
If a single name appeared or disappeared, the file is left untouched and the
reason is printed. This is a structural guarantee, not a code review promise.

**It leaves statements that do not own their line alone.** In
`import a; import b` and `x = 1; import os`, moving the import would drag
the other statement with it, so the line is pinned.

**It only touches module-level imports.** Imports inside `try:` blocks,
inside `if TYPE_CHECKING:`, and inside functions are never moved — their
order is part of the program's logic, not its style.

**It keeps your comments where you put them.** A comment on its own line,
separated from the imports around it by blank lines, is treated as a section
heading and splits the block: nothing is sorted across it.

**It honours the markers already in your files.** `# isort: skip` pins a
statement, `# isort: off` / `# isort: on` pin a region, and `# isort: skip_file`
pins the file. They are read as-is, so choices you made on purpose survive a
run.

**It never moves a shebang or a coding cookie.** Those two lines belong to
the interpreter, not to your imports.

## Not for you if

- You want the tool to decide how a long import is wrapped. That is a
  formatter's job — run `black` after this, not instead of it.
- You want imports sorted inside `if TYPE_CHECKING:` blocks. They are
  deliberately left alone.
- You need it to be as fast as a compiled binary. It is plain Python; on
  600 files it takes about 15 s (see below).

## Measured

600 real files (CPython's `Lib` plus this project family), no configuration:

| | result |
|---|---|
| Files changed | 248 |
| Files where a comment changed | **0** |
| Files where the set of imported names changed | 0 |
| Files changed again on a second run | 0 |
| Wall clock | 15.2 s |

The two invariants that matter are the middle rows: the tool may move a line,
but it may not rewrite a comment or change which names are imported. Before
writing, it re-parses the result and compares the import set; if anything
changed, the file is left alone.

A second run is a no-op, so the tool is safe to put in a pre-commit hook.

## 中文速览

`importsift` 只做一件事：把 Python 文件顶部的 import 分成五组
（`__future__` / 标准库 / 第三方 / 本项目 / 相对导入），排好序，并告诉你每一条为什么去了那一组。

它不读配置文件。名字属于哪一组，是查出来的：标准库查解释器自己的
`sys.stdlib_module_names`，本项目的查磁盘上有没有对应的文件，第三方查
`site-packages`。工作目录完全不参与判断，所以同一个文件在本地和 CI 上结果一样。

它也不重写你的 import。整行原样搬走，注释跟着走，括号里被注释掉的名字
不会被揉成一行。写回之前会重新解析一遍，import 集合只要变了就不写。

```console
$ python importsift.py --explain app.py   # 每条 import 的依据
$ python importsift.py --check .          # 只检查，有问题返回 1
$ python importsift.py .                  # 就地整理
```
